## Known limits and risks (accept or fix)
| # | Item | Detail |
|---|---|---|
| R1 | **Account switch in another tab: identity binding of JSON answers still uses email** | **Writes are closed (F2.4):** every application write sends `X-Applicant-Id`, and Rails refuses any other id, or none, with `409 identity_mismatch` before reading or writing (see Resolved). **Photo reads are bound by id (F2.3)** through `X-Applicant-Id` on `GET …/passport_photo`. **Still open:** JSON answers (GET, stage saves, Load latest) are checked against the `/me` email, which relies on emails being unique and never changing. That is true today, since there is no email-change feature. Returning the user id in `applicant` and comparing ids would close this. Revisit if email changes are ever allowed |
| R2 | **Expired sessions are noticed only on interaction** | A tab left visible keeps showing the last page until the user focuses it again, navigates or makes a request. The server is still the authority. No data changes without a valid session |
| R3 | **Two tabs and CSRF** | After a login, logout or reset in one tab, the other tab's first request gets 403, then fetches a new token. The code handles this, but it has no end-to-end test. **Wording:** application stage saves say "We couldn't verify this request. Please try again." The auth pages still say "Your session expired. Please try again." for any 403. Align them if a 403 there shouldn't imply an expired session |
| R5 | **Offline behaviour** | Since F2.2, every request fails at once when the browser is offline (`networkMode: "always"` in `createQueryClient`, `Frontend/src/lib/api.ts`) and shows "We couldn't reach the server…". Nothing is paused or re-sent when the connection returns: the user retries. This is deliberate, so a save is never silently resent with an old `lock_version` |
| R6 | **Unsaved typing is lost if the tab closes** | With no autosave (P2) and no "unsaved changes" warning, values typed but not saved are gone after closing or reloading the tab. Saved drafts persist (checked in the browser) |
| R7 | **`apply-page.tsx` is about 1,620 lines (technical debt, scheduled)** | It holds the page, the shared stage-form code (`useStageForm`, `StageFooter`, `StageSaveError`, `PhoneInput`, `listedOrOther`, `NativeSelect`) and three stage forms. **Before F2.5 or F2.6**, do a move-only extraction of each stage form and the shared form code into their own files, with no behaviour change and the existing tests unchanged |
| R8 | **Saved photo dimensions are never recorded** | Since F2.3 the passport photo is stored as already "analyzed", so Active Storage's analyze job never runs (see Resolved). Blob metadata has no width or height. Nothing uses them today; a future reviewer screen that needs them must read the image. **This is a workaround, not the only possible fix.** Alternatives include analysing synchronously inside the upload request before responding, or analysing without touching the application row; each needs its own locking review. **Any future attachment on a versioned record has the same hazard:** a background job that touches the row after the response makes the returned `lock_version` stale |
| R9 | **The date picker popover is non-modal (decided)** | Accepted for F2.3: no focus-trapping dialog. Checked in Chromium at 768px: Enter opens on the chosen day (or today); arrows, Home/End and PageUp/PageDown move between days and months; Enter picks; **Escape closes and returns focus to the date field**; **Tab from the days closes the calendar and moves on to the next field** (Sex); Shift+Tab reaches the month and year dropdowns. No keyboard trap, and axe reports no violations. Revisit only if an accessibility audit asks for the WAI-ARIA modal date-picker dialog |
| R4 | **Bundle size** | The production JS is 735 kB (228 kB gzipped) after F2.4. The shadcn Calendar date picker (react-day-picker, which brings date-fns) added about 170 kB (54 kB gzipped); lazy-loading the stage forms would keep it off the sign-in pages. Vite warns about chunks over 500 kB. Consider route-level code splitting before the dashboard grows it |

## Resolved (kept for traceability)
| Item | Resolved in | How |
|---|---|---|
| Photo upload returned an outdated `lock_version`, so the next save got a false `409 stale` | F2.3 | Found in the real-browser walkthrough (unit tests mock Rails and couldn't see it). Active Storage's background analyze job updated the blob after the response, which touched the application row and raised `lock_version` once more. Fixed in `MembershipApplication#passport_photo_file=` by storing the blob as already analyzed (`metadata: { analyzed: true }`), The controller test proves no analyze job is enqueued, that `lock_version` doesn't move after the response (for both a first upload and a replacement, with the purge job run), that a Personal save with the returned version succeeds, and that a save with the pre-upload version still gets `409 stale` without overwriting. It fails without the fix. Optimistic locking, the stale-upload rollback and the photo checks are unchanged. See R8 |
| A save from a tab still showing applicant A could be written into applicant B's application | F2.4 | Found in the F2.4 browser walkthrough and reproduced against Rails. The bug was present from F2.2. After B signed in from another tab of the same browser, A's tab saved with B's session cookie, and Rails wrote A's details into B's application whenever the two `lock_version`s matched (likely, since they are small counters). The browser's identity check only ran on the answer, after the write. Fixed at the source: every application write (start, stage save, photo upload, and the future submission) sends `X-Applicant-Id` from `/me` (`writeFor`, `Frontend/src/lib/api.ts`). Rails' `require_expected_applicant` refuses any other id, or none, with `409 identity_mismatch` before reading or writing. The tab then shows "You signed in to a different account…", rechecks `/me` and becomes the new applicant's own form. Rails, frontend and browser tests cover it, including the matching-version case; they fail without the fix |
| Saved passport photo vanished after Continue → Back, refresh or signing in again | F2.3 | The preview was only an in-memory URL of the file just picked, held in the form's state. The saved photo is now fetched from `GET …/passport_photo` (`passportPhotoQuery`, `Frontend/src/lib/api.ts`) and kept in TanStack memory only: never in browser storage, removed with the session by `forgetSession`, keyed by user id and the blob `checksum` (new in the application JSON) so a replacement is a new entry. Rails names the owner in `X-Applicant-Id`; a photo answered for another sign-in (account switched mid-request) is dropped and `/me` is rechecked. A confirmed upload shows the uploaded file at once, without downloading it again. Object URLs are revoked when the image changes or unmounts. Loading and failure states, with a retry |
| A tab switched to another sign-in could keep the previous applicant's typed values | F2.3 | Found while verifying the photo preview (it dates from F2.2). The stage forms weren't keyed by user. If another applicant's application was already cached in the tab, the form stayed mounted with the previous applicant's values and `lock_version`, and a save could have written them into the other application. Each stage form is now keyed by the `/me` user id, with a test that fails without the key |
| Date picker keyboard navigation did nothing | F2.3 | Found in the 768px browser walkthrough. The shadcn-generated `CalendarDayButton` (`Frontend/src/components/ui/calendar.tsx`) created a ref for react-day-picker's keyboard focus but never attached it, so the arrow keys moved nothing and changing month dropped focus. Fixed by passing `ref={ref}`, with a component test that fails without it. Also from that walkthrough: axe flagged `aria-required` on the date button (not allowed on buttons); "required" is now part of its accessible name. Re-check this ref if `calendar.tsx` is ever regenerated with the shadcn CLI |
| Stage forms duplicating save and conflict logic | F2.3 | Employment's draft, save, Load latest and footer moved unchanged into `useStageForm` and `StageFooter` (`Frontend/src/pages/apply-page.tsx`), which Personal reuses. The photo upload shares `useSaveStage`'s cache, identity, 401 and `already_submitted` handling through `useApplicationWrite` (`Frontend/src/lib/api.ts`). Every F2.2 Employment test passes unchanged |
| Shared stage save, "Save and continue later", `409` handling (formerly part of P2) | F2.2 | `useSaveStage` (`Frontend/src/lib/api.ts`) saves with the `lock_version` the form's values were loaded with, and background refetches never advance it. `409 stale` keeps the typed values and offers "Load latest saved version", which is never automatic and shows Loading, errors and retry. `409 already_submitted` reloads into the read-only screen |
| R1 frontend part: cross-account answers rendered or cached | F2.2 | `IdentityMismatch` email check on every application answer. The backend part is still open (see R1) |
| Endless "Loading…" or "Saving…" while offline | F2.2 | Found in the real-browser walkthrough: TanStack Query pauses requests offline by default. Fixed with `networkMode: "always"` (R5), with a regression test |
| Cached applications leaking between users on a shared computer | F2.1 | User-keyed cache (`applicationQuery`) and `forgetSession`. Cached applications are removed whenever Rails reports the session over |
