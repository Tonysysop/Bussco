## Known limits and risks (accept or fix)
| # | Item | Detail |
|---|---|---|
| R1 | **Account switch in another tab: identity binding of JSON answers still uses email** | **Writes are closed (F2.4):** every application write sends `X-Applicant-Id`, and Rails refuses any other id, or none, with `409 identity_mismatch` before reading or writing (see Resolved). **Photo reads are bound by id (F2.3)** through `X-Applicant-Id` on `GET …/passport_photo`. **Still open:** JSON answers (GET, stage saves, Load latest) are checked against the `/me` email, which relies on emails being unique and never changing. That is true today, since there is no email-change feature. Returning the user id in `applicant` and comparing ids would close this. Revisit if email changes are ever allowed |
| R2 | **Expired sessions are noticed only on interaction** | A tab left visible keeps showing the last page until the user focuses it again, navigates or makes a request. The server is still the authority. No data changes without a valid session |
| R3 | **Two tabs and CSRF** | After a login, logout or reset in one tab, the other tab's first request gets 403, then fetches a new token. The code handles this, but it has no end-to-end test. **Wording:** application stage saves say "We couldn't verify this request. Please try again." The auth pages still say "Your session expired. Please try again." for any 403. Align them if a 403 there shouldn't imply an expired session |
| R5 | **Offline behaviour** | Since F2.2, every request fails at once when the browser is offline (`networkMode: "always"` in `createQueryClient`, `Frontend/src/lib/api.ts`) and shows "We couldn't reach the server…". Nothing is paused or re-sent when the connection returns: the user retries. This is deliberate, so a save is never silently resent with an old `lock_version` |
| R6 | **Unsaved typing is lost if the tab closes** | With no autosave (P2) and no "unsaved changes" warning, values typed but not saved are gone after closing or reloading the tab. Saved drafts persist (checked in the browser) |
| R8 | **Saved photo dimensions are never recorded** | Since F2.3 the passport photo is stored as already "analyzed", so Active Storage's analyze job never runs (see Resolved). Blob metadata has no width or height. Nothing uses them today; a future reviewer screen that needs them must read the image. **This is a workaround, not the only possible fix.** Alternatives include analysing synchronously inside the upload request before responding, or analysing without touching the application row; each needs its own locking review. **Any future attachment on a versioned record has the same hazard:** a background job that touches the row after the response makes the returned `lock_version` stale |
| R9 | **The date picker popover is non-modal (decided)** | Accepted for F2.3: no focus-trapping dialog. Checked in Chromium at 768px: Enter opens on the chosen day (or today); arrows, Home/End and PageUp/PageDown move between days and months; Enter picks; **Escape closes and returns focus to the date field**; **Tab from the days closes the calendar and moves on to the next field** (Sex); Shift+Tab reaches the month and year dropdowns. No keyboard trap. **Correction (F2.5):** axe 4.x with the calendar *open* reports `aria-dialog-name` (the popover has no accessible name) and `label-content-name-mismatch` on the day buttons (react-day-picker names them "Sunday, November 1st, 2026" while showing "1"). Both appear on the F2.3 date of birth picker too, so they predate F2.5; with the calendar closed there are no violations at 375, 768 or 1280px. Naming the popover is a one-attribute fix. Revisit only if an accessibility audit asks for the WAI-ARIA modal date-picker dialog |
| R10 | **Rails' minimum-contribution message is in kobo** | A Rails `422` on `monthly_contribution_kobo` would read "Monthly contribution must be greater than or equal to 3000000". The form checks the minimum first, using the `policy` in the same application response, so users see it only if the policy changes while their page is open. A custom message in the model would close it |
| R4 | **Bundle size** | The production JS is 856 kB (263 kB gzipped) after A1.4 (767 kB after A1.2, 751 kB after F2.6; the A1.4 Super Admin pages added about 89 kB; the admin pages added 16 kB; their fonts and watermark are separate files loaded only on admin pages). The shadcn Calendar date picker (react-day-picker, which brings date-fns) added about 170 kB (54 kB gzipped); lazy-loading the stage forms would keep it off the sign-in pages. Vite warns about chunks over 500 kB. Consider route-level code splitting before the dashboard grows it |

| R11 | **The admin role audit is append-only only through the application** | `AdminRoleChange` rows are read-only in Active Record, and a validation rejects any role change except `User#change_admin_role!`. Privileged database access (SQL, `update_columns`, a Rails console) can still change roles without an audit row, or edit and delete audit rows. For tamper resistance, restrict production DB grants and/or ship audit rows off the box |
| R13 | **An ended admin session is noticed on navigation, focus or refresh** | The admin guard re-asks Rails on route changes and window focus once its cached answer is 30 s old, and always on refresh. An admin page left open without interaction keeps showing until then (Rails still refuses every admin request). After a **refresh** the page can't tell "expired" from "never signed in" (the cookie is HttpOnly and Rails deletes it), so it shows the plain admin login; the "Your session has expired" notice appears only when an in-app check turns a known admin into no session. Revoked and disabled admins see the same generic notice |
| R14 | **The role-change history loads in one request** | `GET /api/v1/admin/role_changes` returns every row with no pagination (`shortcut:` in `role_changes_controller.rb`), and the Audit Log searches it in the browser. Fine while role changes are rare; add a cursor when the history passes a few hundred rows |
| R12 | **Admin login and member tabs share the CSRF session** | Admin and member auth sessions are isolated (separate cookies and rows), but both logins rotate the one Rails CSRF session, so an open member tab gets one `403` and then fetches a new token (as in R3) |

## Resolved (kept for traceability)
| Item | Resolved in | How |
|---|---|---|
| Super Admin management portal (was P8) | A1.4 | `/admin` (Overview), `/admin/roles` and `/admin/audit` for the Super Admin only (`RequireSuperAdmin`; Rails enforces `require_admin_role(:super_admin)` on every endpoint). One holder per office (validation + partial unique index); assigning an occupied office demotes the holder in the same transaction with two audit rows, and all role changes serialize on one advisory lock. Portal audit rows record the acting admin's id (`changed_by_user_id`). The Super Admin can't manage itself or the system account.
